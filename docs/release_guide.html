PHASE 2

Cryptographic App Signing & Keystore

🚨
CRITICAL DATA INTEGRITY WARNING:
For direct APK distribution, Android enforces that app updates MUST be signed with the exact same keystore. If you lose this keystore or re-generate it later with different keys, your users will receive an App not installed as package appears to be corrupt / signature mismatch error and will have to uninstall their app—permanently losing their local health database! Back up your keystore securely.
Generate Production Release Keystore
Execute Java's keytool utility to create a 2048-bit RSA upload keystore with a 10,000-day validity in the android/app directory.
POWERSHELL (RUN FROM PROJECT ROOT) 
keytool -genkey -v -keystore android/app/upload-keystore.jks -storetype JKS -keyalg RSA -keysize 2048 -validity 10000 -alias upload
Create `android/key.properties` Template
Create the configuration file in android/key.properties holding passwords and aliases (never committed to git).
FILE: android/key.properties 
storePassword=<your-keystore-password>
keyPassword=<your-key-password>
keyAlias=upload
storeFile=upload-keystore.jks
Verify `.gitignore` Exclusions
Ensure key.properties, *.jks, and *.keystore are strictly ignored by Git so private release keys are never leaked to public GitHub repositories.
SNIPPET IN: .gitignore 
# Release Keystore & Secrets
key.properties
**/android/key.properties
*.jks
*.keystore
PHASE 3

ProGuard Rules & R8 Shrinking

Create ProGuard Rules (`android/app/proguard-rules.pro`)
Protect native Android interfaces used by Sqflite, File Picker, Printing, and Share Plus from being stripped during R8 optimization.
FILE: android/app/proguard-rules.pro 
# Flutter Wrapper
-keep class io.flutter.app.** { *; }
-keep class io.flutter.plugin.**  { *; }
-keep class io.flutter.util.**  { *; }
-keep class io.flutter.view.**  { *; }
-keep class io.flutter.**  { *; }
-keep class io.flutter.plugins.**  { *; }

# SQLite native hooks
-keep class com.tekartik.sqflite.** { *; }

# PDF & Printing native interfaces
-keep class net.nfet.flutter.printing.** { *; }

# File Picker & Share Plus
-keep class com.mr.flutter.plugin.filepicker.** { *; }
-keep class dev.fluttercommunity.plus.share.** { *; }

# Keep generic attributes
-dontwarn javax.annotation.**
-keepattributes *Annotation*,EnclosingMethod,Signature
Configure Gradle Release Signing & Shrinking
Update android/app/build.gradle.kts to automatically load keystore credentials and enable release shrinking with Proguard rules.
SNIPPET FOR: android/app/build.gradle.kts 
import java.io.FileInputStream
import java.util.Properties

val keystoreProperties = Properties()
val keystorePropertiesFile = rootProject.file("key.properties")
if (keystorePropertiesFile.exists()) {
    keystoreProperties.load(FileInputStream(keystorePropertiesFile))
}

android {
    ...
    signingConfigs {
        create("release") {
            keyAlias = keystoreProperties["keyAlias"] as String?
            keyPassword = keystoreProperties["keyPassword"] as String?
            storeFile = keystoreProperties["storeFile"]?.let { file(it) }
            storePassword = keystoreProperties["storePassword"] as String?
        }
    }

    buildTypes {
        release {
            signingConfig = signingConfigs.getByName("release")
            isMinifyEnabled = true
            isShrinkResources = true
            proguardFiles(
                getDefaultProguardFile("proguard-android-optimize.txt"),
                "proguard-rules.pro"
            )
        }
    }
}

LIFECYCLE

First-Time Setup vs. Next Update Steps

🚨
CRITICAL RULE: NEVER RUN flutter run ON A PHONE WITH A SIGNED RELEASE APP
Standard flutter run installs a Debug APK signed with Android's generic debug certificate. If your phone already has the signed release APK:
  • Android will reject the update with INSTALL_FAILED_UPDATE_INCOMPATIBLE (signature mismatch).
  • If you uninstall the app to force debug mode, Android will permanently wipe your local SQLite database (all family members and health logs will be lost).
  • Always update existing release installs using a new Signed Release APK via adb install -r.
🌱

1. First-Time Setup (Initial Release)

Perform these configuration steps only once when initializing your production pipeline:

  1. Generate Keystore: Run keytool to create health-tracker-release.jks in a secure directory.
  2. Configure Credentials: Create android/key.properties with passwords, key alias, and path to the keystore.
  3. Protect in Git: Verify key.properties and *.jks are listed in .gitignore so private keys never leak.
  4. Set R8 Rules: Add native keep rules in android/app/proguard-rules.pro and enable shrinking in build.gradle.kts.
  5. Initial Version: Set version: 1.0.0+1 in pubspec.yaml.
  6. Compile & Install: Build the first signed release APK and install via adb install.
🚀

2. Subsequent Updates (New Versions)

Follow this quick 5-step checklist for every subsequent update (e.g., v1.0.1, v1.0.2...):

  1. Keep Keystore Untouched: Always use the exact same keystore and key alias so Android recognizes the app author.
  2. Bump Version: Increment version: X.Y.Z+N in pubspec.yaml and update the footer in settings_screen.dart.
  3. DB Check: If tables or columns changed, bump DB version and write migration in _upgradeDB. (Never drop tables!)
  4. Compile Release APK: Run flutter build apk --release ...
  5. In-Place Install: Run adb install -r ... to preserve all user database records.

Step-by-Step Production Update Commands

Step 1: Bump version in pubspec.yaml (Increment both SemVer and build integer):

pubspec.yaml 
# Format: version: MAJOR.MINOR.PATCH+BUILD_NUMBER
version: 1.0.1+2

Step 2: Compile the new signed Release APK:

Step 3: Perform In-Place Update on Connected Android Phone (keeps data intact):

POWERSHELL / ADB

Step 4: Tag & Commit the Update:

GIT COMMANDS

git commit -m "chore(release): bump version to 1.0.1+2"
git tag -a v1.0.1 -m "Release v1.0.1: Graph tooltip contrast and UI polish"
git push origin main --tags

Part Example When to Increment Target Audience
PATCH 1.0.1 Bug fixes, UI contrast adjustments, small tweaks End Users (SemVer)
MINOR 1.1.0 New features added without breaking changes (e.g. Medicine reminders) End Users (SemVer)
MAJOR 2.0.0 Major redesigns or breaking database schema overhauls End Users (SemVer)
BUILD NUMBER +2 (after +) Every single release without exception (must always increase: 1, 2, 3...) Android OS (versionCode)

Safe Database Evolution Rules

Because direct APK users update by installing new APKs on top of existing installs, adhere to these 3 unbreakable rules:

  • Never drop tables or alter db.delete in database_helper.dart for production updates.
  • Always bump version (e.g. from 3 to 4) and write an explicit if (oldVersion < 4) { await db.execute('ALTER TABLE ... ADD COLUMN ...'); } in _upgradeDB.
  • Always bump pubspec.yaml version (e.g., 1.0.1+2) so Android recognizes the APK as a newer build.
